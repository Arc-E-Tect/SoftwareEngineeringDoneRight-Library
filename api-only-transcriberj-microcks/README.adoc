The Microcks emitter of the https://github.com/Arc-E-Tect/SoftwareEngineeringDoneRight-API/tree/main/api-only-transcriberj[API-Only TranscriberJ ↗]: for every `send` operation of an API contract's AsyncAPI document, a generated JUnit 5 test that checks what an application actually publishes against a Microcks-imported copy of the contract.

== Using it

Add it to the TranscriberJ's emitter configuration:

[source,groovy]
----
dependencies {
    transcriberjEmitters 'com.arc-e-tect:api-only-transcriberj-microcks:1.3.2'
}
----

The TranscriberJ loads it in a class loader of its own and adds `io.github.microcks:microcks-testcontainers` and `org.testcontainers:testcontainers` to the source sets it generates into, at 0.5.0 and 2.0.5, unless the project declares versions itself.
A microcks-testcontainers version from 0.6.0 on, or a Testcontainers version from 2.1.0 on, is reported as not tested with this emitter.

Only `send` operations are represented: verifying that an application correctly reacts to a message it *received* needs a different harness shape, and is left for a later emitter.
An AsyncAPI document without a `send` operation generates nothing.

== What it generates

One interface per contract, `<basePackage>.microcks.AsyncConformanceHarness`, carrying:

[cols="1,3",options="header"]
|===
|Member |What it is

|`@Test default void <operationId>_conformsToContract()`, one per `send` operation
|Generates an isolation-suffixed channel address, asks Microcks to listen on it, waits `subscriptionDelay()` for it to subscribe, calls the operation's hook (below) to publish on it, and asks Microcks whether what it received conforms to the contract.
It publishes once, and asserts on Microcks' verdict on that one message: see `resultTimeout()`.

|`void <operationId>(String suffixedChannel)`, one per `send` operation, abstract
|What a generator cannot know: how the application publishes that operation's message, on the suffixed channel it is given, exactly as production code would. It must not return before the message has been sent -- flush a buffering producer. The project implements one of these per operation.

|`void wireBroker(MicrocksContainersEnsemble ensemble)`, abstract
|Start the application's message broker on `ensemble.getNetwork()`, and connect the ensemble to it, before the ensemble starts. Which broker, and so which Testcontainers module wires it, is the project's own choice.

|`Path contractFile()`, abstract
|Where the build put the fetched AsyncAPI document, for Microcks to import. The emitter cannot know this: it depends on the project's own build layout.

|`String endpoint(String suffixedChannel)`, abstract
|Turn a suffixed channel address into the endpoint Microcks tests against, in the broker's own address form -- `"kafka://kafka:9092/" + suffixedChannel + "?startOffset=0"`, for instance.
For Kafka, add `startOffset=0`: see <<kafka,Kafka §>>.

|`Duration subscriptionDelay()`
|How long a test waits, after asking Microcks to listen and before publishing, for it to have subscribed.
One second by default; override it for a slower broker.
A message published before Microcks has subscribed is missed, unless the broker lets Microcks read it afterwards, as Kafka does with `startOffset=0`.
A delay is not a reliable way to cover the first test: see <<kafka,Kafka §>>.

|`Duration testTimeout()`
|How long Microcks listens on the channel for the published message. Ten seconds by default; override it for an application or broker that takes longer to deliver.

|`Duration resultTimeout()`
|How long a test waits, after publishing, for Microcks to report its result.
`testTimeout()` plus five seconds by default, so overriding `testTimeout()` alone is enough.
Microcks reports only after listening for all of `testTimeout()`, and its async minion can take a few seconds longer on the first test, while it is still cold.
`microcks-testcontainers` waits only one second past `testTimeout()`, and then returns a result that is still in progress, so the test asks Microcks again until the result is final or `resultTimeout()` has passed.
A test that still has no verdict then fails, saying that Microcks had not finished rather than that the message does not conform.

|`String microcksImage()`
|The Microcks image the ensemble runs: `MICROCKS_IMAGE`, the one this emitter was tested with, unless the project overrides it. See <<other-image,Using another Microcks image §>>.

|`SERVICE_NAME`, `MICROCKS_IMAGE`
|The AsyncAPI document's own `info.title` and the Microcks image this emitter was tested with, read at runtime from a properties resource this emitter generates (`META-INF/apionly/microcks/<contract>.properties`). It is regenerated on every build, so it is not a place to configure anything: the service name follows the contract's title, and the image is the one this emitter was tested with.
|===

The interface runs with `@TestInstance(Lifecycle.PER_CLASS)`: one Microcks ensemble for every test it declares, not one per test, so `wireBroker` and `contractFile` run once, before any operation's test, and stop once after the last.

[source,java]
----
class UserAccountAsyncConformanceTest implements AsyncConformanceHarness {

    static KafkaContainer kafka;

    @Override
    public void wireBroker(MicrocksContainersEnsemble ensemble) {
        kafka = new KafkaContainer(DockerImageName.parse("apache/kafka:3.9.0"))
                .withNetwork(ensemble.getNetwork()).withNetworkAliases("kafka")
                .withListener("kafka:19092");   // for the Microcks containers, on the network
        kafka.start();
        awaitConsumerGroupReadiness(); // see "Kafka", below
        ensemble.withKafkaConnection(new KafkaConnection("kafka:19092"));
    }

    @Override
    public Path contractFile() {
        return Path.of("build/api-spec/user-account/asyncapi.yaml");
    }

    @Override
    public String endpoint(String suffixedChannel) {
        return "kafka://kafka:19092/" + suffixedChannel + "?startOffset=0";
    }

    @Override
    public void publishRegistrationInitiated(String suffixedChannel) {
        auditEventPublisher.publish(suffixedChannel, someRegistrationInitiatedEvent());
    }

    // one such method per send operation ...
}
----

The broker has two addresses, and each side uses its own.
The Microcks containers reach it on the Docker network, through the listener `withListener` adds, so `KafkaConnection` and `endpoint` use `kafka:19092`.
The tests run on the host, so the application's producer, and the readiness probe below, use `kafka.getBootstrapServers()`, which is the port Testcontainers maps to the host and is not reachable from inside another container.

[#kafka]
== Kafka: the first operation's test

On a freshly started Kafka broker, the first operation's test can fail with Microcks' verdict `Timeout: no message received`, while every later test passes.
A longer `testTimeout()` or `subscriptionDelay()` is not a reliable way to fix it.
Two things together are, and a project wiring a Kafka broker should do both.

=== Read each test's topic from offset 0

Microcks' Kafka consumer starts at the latest offset, which is fixed only once Kafka assigns it its partition.
For the first test, Microcks creates that consumer while it is still cold, and it can be assigned its partition after the test has published, so it never reads the message.
Later tests' consumers are assigned well within `subscriptionDelay()`.

Add Microcks' `startOffset=0` endpoint option in `endpoint(String)`, as in the example above.
Every test publishes to a topic of its own, suffixed for isolation, so offset 0 is that test's message and nothing else.

=== Wait until the broker can serve a consumer group

A started broker accepts connections, but creates the internal `__consumer_offsets` topic its group coordinator needs only when the first consumer group asks for it.
Without a wait, that first group is Microcks' consumer for the first test, which then spends its listening time waiting for the broker.

In `wireBroker`, after starting the broker and before the ensemble starts, join a consumer group and poll until it is assigned a partition:

[source,java]
----
private static void awaitConsumerGroupReadiness() {
    long deadline = System.nanoTime() + Duration.ofSeconds(90).toNanos();
    try (KafkaConsumer<String, String> consumer = new KafkaConsumer<>(Map.of(
            ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, kafka.getBootstrapServers(),
            ConsumerConfig.GROUP_ID_CONFIG, "consumer-group-readiness-" + UUID.randomUUID(),
            ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName(),
            ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName()))) {
        consumer.subscribe(List.of("consumer-group-readiness"));
        while (consumer.assignment().isEmpty()) {
            if (System.nanoTime() > deadline) {
                throw new IllegalStateException("The Kafka broker could not serve a consumer group in time.");
            }
            consumer.poll(Duration.ofMillis(500));
        }
    }
}
----

This waits until the broker is ready, not for a fixed time, and fails saying so if it never is.
It needs `org.apache.kafka:kafka-clients` in the test source set; the emitter does not add it, because which broker a project uses is its own choice.
On a CI runner this wait was about three seconds, which would otherwise come out of the first test's listening time.

== Using another Microcks image

The generated tests run against the Microcks image this emitter was tested with, `quay.io/microcks/microcks-uber:<tag>`, named by `MICROCKS_IMAGE` in the generated interface.
A project that wants another -- one mirrored in a private registry, or a newer Microcks -- overrides `microcksImage()`:

[source,java]
----
@Override
public String microcksImage() {
    return "registry.example.com/mirror/microcks-uber:1.14.0";
}
----

Nothing else changes, and the emitter does not check the image.
When the ensemble starts with an image other than the tested one, the harness logs a warning (a `System.Logger` at `WARNING`, on the logger named after `AsyncConformanceHarness`):

[source,text]
----
Microcks image '<image>' is used instead of '<tested image>', the one the generated tests were tested with, so they may not work with it. If a test behaves unexpectedly, run it with the default image first: stop overriding microcksImage().
----

The image is a choice of the project, and so is the risk: a different Microcks can change how it validates a message, or what its test API returns, and the generated tests were written against one version.
*If a test fails, hangs or reports something you did not expect with another image, run it with the default first.*
If it passes there, the difference is the image, not your application or the contract; if it fails there too, it is not the image.
Report a problem with the default, not with an override.

The default is the image of the emitter version you use, and moves with the emitter.
There is no property or system property for it: the properties resource the harness reads is regenerated on every build, so it is not a place to configure anything.

[#testcontainers-2x]
== Testcontainers 2.x

`microcks-testcontainers` 0.5.0 is built against the Testcontainers 2.x line.
Gradle resolves Testcontainers core to the highest version anything asks for, so a project that pins 1.x for core still gets 2.x.
In the reference implementation that resolved to core 2.0.5 beside the 1.21.4 `org.testcontainers:kafka` module, and the generated tests passed; other combinations are untested here.
A project that pins Testcontainers deliberately should check what its build resolves, with `dependencyInsight`.

== Development

[source,console]
----
cd api-only-transcriberj-microcks
./gradlew check
./gradlew publishToMavenLocal
----

The tests run the TranscriberJ over a copy of the reference implementation's user-account contract with this emitter, and compile what comes out against `microcks-testcontainers`.
They do not start a real Microcks ensemble or a real broker: that is exercised where a project actually implements the harness's hooks.
How a test waits for Microcks' verdict is tested against a stand-in for Microcks' REST API, an HTTP server that answers with a result still in progress before it answers with a final one.
`check` gates on 90% instruction coverage and on Javadoc without warnings.
