The Domain Validation API Rules project publishes the `architecture-validator-domain-validation-rules` rule pack.
It checks the structure of the https://github.com/Arc-E-Tect/SoftwareEngineeringDoneRight-Patterns/blob/main/patterns/domain-validation-api/domain-validation-api-pattern.adoc[Domain Validation API pattern ↗] in a bounded context's service.
It is consumed by the Architecture Validator plugin as an external rule pack dependency, next to the built-in Hexagonal rules and the `hexagonal-spring-rules` pack.

== Build

Run from this project directory.

[source,bash]
----
./gradlew clean build
----

`./gradlew publishToMavenLocal` publishes the pack to the local Maven repository, for a consuming project to try before a release.

== Adding the Dependency

Add it to `testArchitectureImplementation` in a project that already applies the Architecture Validator plugin, and tell it where the bounded context keeps its validations.

.Gradle (Groovy DSL)
[source,groovy]
----
architectureValidator {
    basePackage = 'com.example.payments'
    hexagonalArchitecture {
        // The shared verdict model is domain model too, so the built-in rules guard it.
        domainModel = ['..application.domain.model..', '..validation.verdict..']
        namingConventionsEnabled = true
    }
}

dependencies {
    testArchitectureImplementation 'com.arc-e-tect.architecture-validator:architecture-validator-domain-validation-rules:0.0.1'
}

tasks.named('testArchitecture') {
    systemProperty 'architectureValidator.domainValidation.validationsPackages', 'com.example.payments.validation'
}
----

The plugin discovers the rule classes on the classpath and includes them in the generated external rule-pack suite.

== What This Rule Pack Checks

The pack checks what is specific to the Domain Validation API pattern.
Three of the rules in the pattern's "Enforcing the structure" section are already built-in rules of the Architecture Validator plugin, and are not repeated here:

* `use_cases_are_suffixed` is the built-in naming convention for inbound ports, with `namingConventionsEnabled = true`.
* `domain_and_application_do_not_depend_on_adapters` is the built-in `core_layer_must_not_depend_on_adapters`.
* `inbound_adapters_do_not_depend_on_the_domain` is the built-in `inbound_adapters_must_access_application_through_inbound_ports`; it covers the shared verdict model once its package is part of `domainModel`, as in the example above.

Each direct sub-package of a validations package is one validation slice, except the shared packages, such as `verdict`.

[cols="2,3,2",options="header"]
|===
|Rule |Checks |Pattern section

|`DomainValidationRulePackConfigurationTest.validationsPackagesAreConfigured`
|Fails fast when the base package or the validations packages are not set, or a validations package lies outside the base package, so that the pack cannot pass on an empty import.
|-

|`DomainValidationSliceTest.validationSlicesAreIndependent`
|No validation slice depends on another; the shared packages are exempt.
|Package layout; Enforcing the structure; Adding a validation

|`DomainValidationSliceTest.sharedPackagesDependOnNoSlice`
|The shared packages depend on no slice, which would couple every slice to that one.
|Package layout

|`DomainValidationSliceTest.noClassDependsOnMoreThanOneValidation`
|No class depends on the inbound ports of more than one validation: no central service, façade or registry dispatches to several validations.
|Rejected alternatives; Can a single handler serve all validations?

|`DomainValidationControllerTest.controllersDependOnlyOnUseCasesTheirAdapterAndExecution`
|A controller depends only on its own validation's inbound ports, with their commands and results, its own inbound web adapter, the asynchronous execution component, the JDK and Spring.
|Controller and use case; Enforcing the structure

|`DomainValidationControllerTest.controllersImplementAGeneratedApi`
|Every controller implements an interface generated into its slice's `adapter.inbound.web.api` package.
|One handler per validation

|`DomainValidationControllerTest.controllersDeclareNoRequestMappingsOfTheirOwn`
|A controller declares no request mapping, on the class or on a method; its mappings come from the generated interface.
|Can a single handler serve all validations?

|`DomainValidationControllerTest.generatedApiTypesStayInTheirInboundWebAdapter`
|Only a slice's inbound web adapter uses the types generated into its `adapter.inbound.web.api` package.
|Package layout; Keep the API types and the domain out of the adapter's reach

|`DomainValidationInboundPortTest.useCasesTakeACommandAndReturnAResult`
|Every method of a validation's use case takes only commands and returns a result, both of its own validation.
|Keep the API types and the domain out of the adapter's reach; Controller and use case

|`DomainValidationInboundPortTest.useCaseResultsAreSealed`
|Every top-level result type is a sealed interface whose permitted subtypes are records.
|Controller and use case

|`DomainValidationInboundPortTest.commandsAreImmutable`
|Every field of a command is final.
|Controller and use case

|`DomainValidationNamingConventionTest.controllersAreNamedAfterTheirApi`
|Optional: a controller implementing `XyzApi` is named `XyzController`. Runs only when naming conventions are enabled.
|Package layout
|===

A controller is a class in a validation slice that is a Spring `@Controller`, which includes `@RestController`.
Commands are expected in a `command` package, and results in a `result` package, below a validation's inbound port package.

== Architecture Validator Properties

The rules read these system properties.
The Architecture Validator plugin sets the first four from its `architectureValidator` extension; the consuming project sets the `domainValidation` ones on its `testArchitecture` task.

[cols="2,1,3",options="header"]
|===
|Property |Default |Purpose

|`architectureValidator.basePackage`
|-
|Root package to import and validate.

|`architectureValidator.inPorts`
|`..application.port.inbound..`
|Package patterns of the inbound ports.

|`architectureValidator.rules.disabled`
|-
|Comma-separated rule identifiers to skip, in the format `ClassSimpleName.methodName`.

|`architectureValidator.namingConventions.enabled`
|`false`
|Enables the optional naming convention rule.

|`architectureValidator.domainValidation.validationsPackages`
|-
|Required. Comma-separated packages that hold a bounded context's validations, one sub-package per validation, inside the base package.

|`architectureValidator.domainValidation.sharedPackages`
|`verdict`
|Comma-separated names of the sub-packages of a validations package that every validation shares.

|`architectureValidator.domainValidation.executionPackages`
|`com.arc_e_tect.validation.async..`
|Comma-separated package patterns of the asynchronous execution component, which controllers may use.
|===
